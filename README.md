# Грузовые аукционы

SPA для работы с грузовыми аукционами по OpenAPI-схеме. Тестовое задание.

Список аукционов с фильтрами и пагинацией, детальная страница, история ставок,
установка своей ставки. Бэкенда нет, все запросы обслуживает MSW.

## Запуск

```bash
npm ci
npm run dev
```

Открыть http://127.0.0.1:5173

Node >= 22.12.0. Версии зависимостей зафиксированы точно, без `^` —
`npm ci` воспроизводит установку из lock-файла.

### Команды

```bash
npm run dev        # dev-сервер
npm run build      # production-сборка
npm run preview    # просмотр production-сборки
npm run test       # тесты
npm run lint       # Biome
npm run check      # build + test + lint одной командой
```

`npm run check` — то, чем удобно проверить проект целиком.

## Стек

React 19, TypeScript 7, Vite 8, TanStack Router (file-based, `autoCodeSplitting`),
TanStack Query v5, Zustand v5, React Hook Form + Zod v4, MSW 2, Tailwind v4,
Biome, Vitest + Testing Library.

TypeScript в strict-режиме с дополнительно включёнными `noUncheckedIndexedAccess`,
`exactOptionalPropertyTypes`, `verbatimModuleSyntax`.

Структура — Feature-Sliced Design, алиас `@/` → `src/`.

```
src/
  app/        роуты, провайдеры, корневой layout
  pages/      страницы: список, детальная, форма ставки
  widgets/    список аукционов, история ставок
  features/   фильтры, установка ставки
  entities/   auction: ViewModel-типы, мапперы, queryOptions
  shared/     api (клиент, DTO, enum-константы, MSW), ui, lib
```

## Схема API

`openapi.auctions.v0.json` в корне — источник правды. Типы DTO генерируются из неё:

```bash
npx openapi-typescript openapi.auctions.v0.json -o src/shared/api/schema.d.ts
```

Руками типы не пишутся. Значения enum вынесены в `shared/api/enums.ts` и объявлены
как `as const satisfies Record<T, T>` — при расхождении со схемой ломается сборка,
а не рантайм. Строковых литералов статусов в компонентах нет.

### Расхождения между ТЗ и схемой

Места, где текст задания требует того, чего в контракте нет. Ничего не выдумывал,
поведение описано ниже.

**Шаг ставки в карточке списка.** ТЗ просит показывать в карточке текущую цену,
цену за км и шаг ставки. `AuctionListItemTradingPrice` содержит только `start`,
`current`, `current_no_vat` — ни `step`, ни `min`/`max` в списочном DTO нет.
Они есть только в детальной (`AuctionShowTradingPrice`). В карточке показаны
цена с НДС, цена без НДС и цена за км; шаг ставки — на детальной и в форме ставки.

**Количество участников.** ТЗ просит показать его на странице ставок,
в `BetListResponse` такого поля нет. Считаю по числу уникальных `organization_id`
среди неотклонённых ставок. Это единственное место в коде с комментарием,
потому что из схемы решение не следует.

**Мок-словарь городов.** Эндпоинта справочника в схеме нет, словарь свой
(`shared/api/mocks/cities.ts`). Рядом с `load_city` (строка) в схеме есть
`load_gc_id` (число) и `load_range` — они не используются.

**Ответ POST ставки.** У `POST /auctions/{auctionUuid}/bets` в схеме нет схемы
ответа: «проксируется от upstream». Поэтому `setBet` возвращает `unknown`,
а состояние после успеха подтягивается инвалидацией, а не разбором тела.

### Неоднозначности в самой схеме

**`status_mobile` объявлен по-разному в двух эндпоинтах.** В `AuctionListItemTrading`
это инлайн-enum на 6 значений, в `AuctionShowTrading` — `$ref` на `TradingStatus`
с 9. Значения `OnPending`, `ChoosingWinner`, `Accepted` есть только в детальной,
при этом фильтр `status` принимает все 9. В мок-проекции списка сузил до
разрешённых схемой 6, лишние отдаю как `Unknown`; UI умеет отображать все 9.
Похоже на недосмотр в схеме.

**`TradingStatus`:** в `description` перечислено 6 значений, в `enum` — 9.
Источником правды взял `enum`.

**Идентификатор аукциона.** Path-параметр объявлен `format: uuid`. В `main`
единственное поле с `format: uuid` — `order_uid` (`id` — integer, `cargo_num` —
номерная строка), по нему и строится навигация. Если аукцион адресуется другим
идентификатором, это одна строка в `entities/auction/api/queries.ts`.

**Во всех enum есть `Unknown`.** UI отображает его нейтральной подписью,
а не падает и не показывает пустоту.

**Почти вся схема без `required`** (исключения — верхний уровень
`AuctionShowResponse` и `BetListResponse`). Поэтому мапперы защитные насквозь,
есть тесты на пустой DTO и на `Unknown`.

## Моки

Все запросы к `/api/v1` обслуживает MSW. Воркер поднимается и в dev,
и в production-сборке — иначе собранное приложение нечем наполнить.

Выключается переменной `VITE_ENABLE_MOCKS` (образец — `.env.example`): любое
значение кроме `'false'` оставляет моки включёнными. С реальным бэкендом
достаточно `VITE_ENABLE_MOCKS=false`, приложение пойдёт в сеть по тем же путям.

Мок-store мутирует по-настоящему. Инварианты (места в рейтинге, победитель,
текущая цена, торговый статус пользователя, границы цены) пересчитываются одной
функцией `recalculate`, общей для генерации фикстур и для обработки POST.
Поэтому состояние после ставки согласовано, а не собрано вручную в хендлере.

44 аукциона генерируются из seeded-PRNG — выдача стабильна между перезапусками.

Ограничения:

- Сборка с `VITE_ENABLE_MOCKS=false` выкидывает весь мок-слой: `dist` худеет
  с 926 до 488 кБ (−47%), чанк `browser-*.js` с `msw` не создаётся вовсе.
- Service Worker браузер разрешает только на `localhost`, `127.0.0.1` или по HTTPS.
  По локальному IP в сети моки не поднимутся, и приложение останется без данных.
- В словаре городов для фильтров (`shared/api/mocks/cities.ts`) эндпоинта нет,
  поэтому он остаётся в бандле и без моков.

## Архитектурные решения

**URL как единственный источник правды для фильтров.** Состояние фильтров живёт
в search params, компоненты читают его через роутер. Двусторонней синхронизации
со стором нет, поэтому нет и класса багов «стор и URL разошлись». Ссылку
с фильтрами можно переслать как есть.

**Zod-схема search params с пофайловым `.catch()`.** Каждое поле откатывается
в безопасное значение независимо от остальных: битый `page` не сносит фильтры,
неизвестное значение enum отбрасывается, остальные остаются. Схема одна и та же
для парсинга и для типизации роута.

**Ключи кэша иерархические**, от общего к частному:
`['auctions']` → `['auctions','list',request]` → `['auctions','detail',uuid]` →
`['auctions','detail',uuid,'bets']`. Инвалидация работает по префиксу:
`auctionKeys.lists()` гасит все страницы списка со всеми комбинациями фильтров,
не перечисляя их.

**После мутации — `invalidateQueries`, а не `setQueryData`.** У POST ставки нет
схемы ответа, значит новое состояние из него не собрать. Плюс ставка меняет не
только цену: пересчитываются места в рейтинге, победитель, торговый статус.
Воспроизводить эту логику на клиенте — значит дублировать серверную. Инвалидация
даёт согласованное состояние ценой одного лишнего запроса.

**Компоненты не видят DTO.** Маппинг DTO → ViewModel в `entities/auction/lib`,
там же форматирование чисел и дат. Компоненты получают готовые строки.
При изменении контракта правится маппер, разметка не трогается — на замене
провизорной схемы настоящей это подтвердилось.

**Мок-store мутабельный, а не набор статичных фикстур.** Требование ТЗ —
чтобы моки реально меняли состояние после мутаций. У фикстур и POST общая `recalculate` —
начальное состояние и состояние после ставки собраны по одним правилам.

**Prefetch по intent.** `onMouseEnter` и `onFocus` на карточке вызывают
`queryClient.prefetchQuery` с теми же `queryOptions`, что использует детальная
страница. Ключ совпадает, поэтому переход по ссылке берёт данные из кэша.
`onFocus` — чтобы работало и с клавиатуры.

**Zustand только под UI-state.** Один стор — очередь тостов. Серверные данные
целиком в TanStack Query, состояние фильтров в URL. Дублирования нет.

## Что проверял

Три уровня: юнит-тесты на чистую логику, браузерные прогоны против
production-сборки, ручной проход.

Браузерные сценарии больше не одноразовые скрипты — они воспроизводятся
командой `npm run e2e`: Playwright сам собирает проект, поднимает `preview`
и гоняет пять сценариев в chromium (фильтр в URL и его восстановление после
перезагрузки, битые search params, empty state, установка ставки с проверкой
обновлённого списка, отсутствие горизонтального скролла на 390px).
В `npm run check` они не входят, чтобы он оставался быстрым.
Ранние прогоны на Chrome DevTools Protocol сохранены в
[browser-checks.md](browser-checks.md) как история проверок.

### Тесты

```bash
npm run test
```

85 тестов в 7 файлах:

| файл | тестов | что покрыто |
|---|---|---|
| `entities/auction/lib/mapAuction.test.ts` | 29 | мапперы DTO → ViewModel, пустой DTO, `Unknown`, подсчёт участников |
| `features/auction-filters/model/searchParams.test.ts` | 27 | парсинг search params, fallback по каждому полю |
| `features/create-bet/model/betSchema.test.ts` | 10 | схема валидации ставки: min, max, кратность шагу, ноль, нечисло |
| `features/auction-filters/lib/buildListRequest.test.ts` | 7 | сборка тела запроса из состояния фильтров |
| `features/create-bet/ui/CreateBetForm.test.tsx` | 5 | 422 в поле формы, 422 в тост, 401, 503, выключенный `can_set_bet` |
| `app/App.test.tsx` | 3 | монтирование трёх страниц, проброс `auctionUuid` |
| `app/integration.test.tsx` | 4 | интеграционные сценарии поверх MSW через настоящий роутер |

Интеграционные тесты идут через `setupServer` и реальный роутер на
`createMemoryHistory`, поэтому разбор search params проходит через `validateSearch`,
а не в обход. Покрыты четыре сценария: клик по фильтру пишет значение в URL
и уходит в теле запроса на сервер; битые search params не роняют страницу,
а соседние фильтры продолжают применяться; фильтр без совпадений даёт empty state,
а не бесконечный скелетон; ставка меняет цену и торговый статус в списке
через инвалидацию.

Проверил, что тесты не декоративные: временно убирал `invalidateQueries` для
списка — падал сценарий со ставкой; убирал `.catch` у `page` — падал сценарий
с битыми search params. Оба изменения откачены.

Серверную 422 браузерным прогоном не достать: клиентский Zod и мок валидируют
по одним правилам, невалидный запрос до сервера не доходит. Ветка
`field` → `setError` покрыта отдельным тестом с подменой хендлера — иначе
осталась бы непроверенной.

### Браузерные прогоны

Полные выгрузки — в `browser-checks.md`. Прогонялись скриптами через Chrome
DevTools Protocol против `vite preview`, то есть против собранного приложения,
а не dev-сервера.

**После перехода на настоящую схему — 38 проверок.** Форма ответа `{ data, meta }`,
пагинация, `status` против `statuses` (разные выборки: 4 против 18), фильтры,
битые search params, empty state, детальная со всеми блоками, форма ставки
по прямой ссылке, отклонение цены выше максимума и некратной шагу, мутация
мок-стора (142 000 ₽ → 139 500 ₽, «Не участвую» → «Лидирую»), докатывание
инвалидации до списка, все четыре флага ограничений, `Unknown`, 404,
отсутствие горизонтального скролла на 390px.

Первый прогон дал один провал: `?statuses=2` роутер отдаёт числом, а не строкой
или массивом, схема откатывала фильтр в `undefined` и он молча не применялся.
Починено ветвью одиночного значения в `listOf`, закрыто тестом.

**После причёсывания UI — 23 проверки.** Отсутствие дублей заголовка, замена
нативных `select multiple` на чекбоксы, равная высота групп, выравнивание строк
сетки, запись значения в URL и восстановление из URL. Провалов нет.

**После сжатия панели фильтров — 23 проверки.** Отсутствие внутреннего скролла
у групп, все значения видны сразу, три колонки на >= 1024px, состояние кнопки
«Сбросить», упаковка полей без дыр, список виден без прокрутки — в первый
экран попадает три карточки.

### Ручной проход

Запускал приложение и проходил сценарии глазами: фильтры и их восстановление
после перезагрузки страницы, пересылка ссылки с фильтрами, битые search params
в адресной строке, переход в детальную и обратно, форма ставки с невалидной
и валидной ценой, 404 на несуществующем uuid, раскладка на 390px и 1440px.

Часть проблем нашлась именно так, а не прогонами: дублирование заголовка
страницы, обрезка последнего пункта в нативных `select multiple`, пустая зона
в сетке фильтров. По ним и делались итерации UI.

## Ограничения

- Шаг ставки не показан в карточке списка — поля нет в списочном DTO
  (см. «Расхождения между ТЗ и схемой»).
- Ставка отправляется как цена с НДС. `SetBetRequest` — это `{ price }`
  без указания базы; валидирую по `trading.price.min/max/step`, двойники
  `_no_vat` показываю в подсказке. В схеме есть `is_last_bet_with_vat` —
  по нему можно было бы определять базу вместо фиксированного выбора.
- Своя организация определяется по `admitted_organizations[].is_main`.
  В реальном приложении пришла бы из сессии.
- Повторная ставка в моке отменяет предыдущую с причиной «Заменена новой
  ставкой», а не редактирует её. `PATCH` схема не описывает.
- Числовые коды статуса аукциона (1–7) для фильтра `statuses` захардкожены
  в `shared/api/enums.ts`: в схеме они упомянуты только в описании поля,
  машиночитаемого маппинга нет.
- В дефолтной сборке моки включены, потому что бэкенда нет.
  Отключаются переменной `VITE_ENABLE_MOCKS=false` — см. раздел «Моки».
- `sort`, `mobile_statuses` и остальные фильтры схемы за пределами
  минимального набора из ТЗ не реализованы.
