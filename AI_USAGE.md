## Что решал сам

**Стек в пределах обязательного.** ТЗ фиксирует React, TS, Vite, TanStack Router
и Query, RHF + Zod, MSW, FSD, Zustand или MobX. Остальное мой выбор: Biome
вместо ESLint + Prettier, Tailwind вместо компонентной библиотеки,
Zustand вместо MobX

**Строгость TypeScript.** Помимо strict включил noUncheckedIndexedAccess,
exactOptionalPropertyTypes, verbatimModuleSyntax. cтоило дополнительной
возни в мапперах, зато почти вся схема без required

**Enum-значения через as const satisfies Record<T, T>.** Расхождение
со сгенерированными типами ломает сборку хоть и  не рантайм. это оказалось
решающим при замене схемы

**URL как единственный источник правды для фильтров**, без синхронизации
со стором. Двусторонний синк известный источник багов. здесь он не нужен

**Пофайловый .catch() в схеме search params** вместо валидации объекта целиком:
битое одно поле не должно сносить остальные фильтры

**Иерархические ключи кэша** с инвалидацией по префиксу чтобы lists()
гасил все страницы со всеми комбинациями фильтров, не перечисляя их

**Инвалидация вместо setQueryData** после мутации. Ставка меняет места
в рейтинге, победителя и торговый статус; воспроизводить это на клиенте
не обязательно, мы дублируемся

**Мутабельный мок-store с общей функцией пересчёта** для фикстур и для POST,
чтобы начальное состояние и состояние после ставки собирались по одним правилам

**Подсчёт участников по уникальным organization_id**  поля в схеме нет,
решение моё, помечено комментарием

**Идентификатор для навигации — order_uid**, потому что path-параметр объявлен
format: uuid, а это единственное поле main с таким форматом

**Мок-слой работает и в production-сборке.** Агент по умолчанию оставил его
только в dev при таком раскладе собранное приложение открывалось бы пустым

## Что проверял особенно внимательно

**Соответствие моков схеме после её замены.**Отдельно сверял руками места, где типы совпадают,
а значение разное:

- status это массив строк торгового статуса пользователя, statuses — массив
  числовых кодов статуса аукциона. Прочитать наоборот легко, и типы не помогут.
  Проверил, что фильтры дают разные выборки: 4 против 18.
- status_mobile объявлен по-разному в списке (инлайн-enum, 6 значений)
  и в детальной ($ref на TradingStatus, 9). Разбирался, какое поведение
  корректно, а не подгонял под один вариант.
- TradingStatus: в описании 6 значений, в enum 9. Взял enum

**Что enum действительно сужается до литералов.** После генерации типов
проверил негативом: невалидное значение auc_type даёт ошибку компиляции,
а не проваливается в any

**Поведение фильтров при битых search params.** Здесь нашёлся
единственный настоящий баг: ?statuses=2 роутер отдаёт числом, схема ждала
строку или массив, фильтр молча откатывался в undefined. Юнит-тест схемы
в отрыве от роутера этого не показывал только браузерный прогон

## Какие риски остались

**Работа начиналась без схемы.** openapi.auctions.v0.json в материалах
не было. Запросил его, а пока восстановил схему из текстового
описания помечая как PROVISIONAL.

Когда пришла настоящая, расхождения оказались структурными: вложенность вместо
плоских объектов, другая пагинация, другие значения всех enum, другой формат
422. Миграция обошлась в один заход: типы генерировались, enum-значения жили
в одном модуле, компоненты работали с ViewModel расхождения показал
компилятор. Пометки PROVISIONAL сняты

**Проксирование вывода агента.** источником требований был PDF со скрытым
текстом. Если бы файл ушёл в агента как есть, инструкция была бы выполнена
молча и я бы об этом не узнал. Это класс рисков, а не единичный случай:
любой входной документ от подрядчика или заказчика может содержать инструкции
в адрес модели

**Ставка отправляется как цена с НДС.** SetBetRequest это { price }
без указания базы. Если бэкенд ждёт цену без НДС, меняется одна константа
в форме

**Числовые коды статуса аукциона захардкожены.** в схеме диапазон 1–7 упомянут
только в описании поля statuses, машиночитаемого маппинга код-значение нет.
Если порядок кодов на бэке другой, фильтр по статусу аукциона будет
фильтровать не то

**Своя организация определяется по admitted_organizations[].is_main.**
Допущение: в реальном приложении это пришло бы из сессии

**Покрытие тестами неравномерное.** Чистая логика покрыта плотно, компоненты
только форма ставки. Виджеты и страницы проверялись браузерными прогонами,
которые в репозиторий не попали: скрипты были одноразовыми, сохранены только
выгрузки в browser-checks.md
